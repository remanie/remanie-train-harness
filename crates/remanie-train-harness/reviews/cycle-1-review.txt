What this change does:
The new Rust executable runs one coding attempt with the eight agreed Grok tools and an OpenAI-compatible Miles session URL. The Python adapter starts that executable and gets a reward from trusted verifier code. I assumed many separate disposable environments, each with one sequential model loop and no shared tool state.

Cycle 1 review, 2026-10-27. This is an independent read-only review of the new crate, assets, tests, adapter, documentation, workspace registration, and lockfile entry. I read the native functions they call and the Miles agent wrapper, session tree, sample assembly, picker, and postprocessor. I made no implementation changes. The findings below record problems reported against the first implementation while the implementers completed it. Their fixes are present in the reviewed source. They are historical findings, not claims that the current lines still contain the old behavior.

Must fix, fixed during this pass:

1. A tool-call response could be reported as a completed answer. Current fix: src/runner.rs:426-435. Regression cases: src/runner/tests.rs, malformed_tool_call_shapes_stop_without_dispatch.
   What this is: The runner decides whether the model wants tools or has finished.
   Problem: A choice with finish_reason="tool_calls" and no tool_calls array passed through has_tools=false and became status="completed" with an empty answer. An object-valued tool_calls field did the same.
   Fix: Validate the field's shape and reject a tool_calls finish without calls before dispatch or completion. The implementation now does this and limits one response to 128 calls.
   If we skip it: Invalid model responses look like completed attempts and can reach the verifier with the wrong outcome label.

2. The compaction trigger ignored the tool output just appended. Current fix: src/runner.rs, new_tool_bytes and the compaction_threshold_tokens comparison. Documentation: README.md:57.
   What this is: The runner decides when to replace old conversation context with a summary.
   Problem: usage.total_tokens describes the model request and generated response, before tool results exist. A response below the configured threshold followed by a large file read could send the next request over the model's context limit without triggering compaction.
   Fix: Include serialized new tool-message bytes and a response reserve. The implementation now uses that conservative estimate and documents that unknown chat templates still require a suitable threshold. It stops on overflow rather than silently deleting messages.
   If we skip it: A valid long task fails when an ordinary tool result pushes its next request over the context limit.

3. Compacting could copy large process logs into the new context. Current fix: src/tools.rs:220-231. Native evidence: crates/codegen/xai-grok-tools/src/computer/task_log.rs, MAX_SNAPSHOT_BYTES, and LocalTerminalBackend::list_tasks_metadata.
   What this is: The summary continuation includes current todo and background-task state.
   Problem: The first implementation used list_tasks(), which reads up to 1 MiB from each completed task log. Several logs could make the replacement context larger than the original context.
   Fix: Use the existing metadata-only task listing. The implementation now retains task IDs, paths and status without inserting logs. The successful compaction test asserts that output is empty and task state survives.
   If we skip it: Compaction can immediately produce another oversized request and waste the summary generation.

Should fix, fixed during this pass:

4. A stalled verifier had no deadline. Current fix: python/miles_grok.py:124-126. Executed regression: test_grader_timeout_is_an_error.
   What this is: The trusted callback grades the workspace after the Rust attempt ends.
   Problem: An asynchronous verifier waiting forever kept the agent call alive after the runner's deadline. There was no score and no error for Miles to handle.
   Fix: Bound the verifier await separately. The adapter now defaults to 60 seconds and returns grader_error on timeout. The required reward hook raises on that outcome instead of returning zero.
   If we skip it: A stalled grading service holds rollout capacity indefinitely.

5. Request journals had no size limit. Current fix: src/runner.rs:164-173 and 205-208. Documentation: README.md:65.
   What this is: The local journal records the full request and response for each model call.
   Problem: With compaction disabled, 100 turns each adding 40 KiB repeat roughly 200 MiB of request history. The prior max_turns ceiling of 10000 allowed far more, and the response/log caps did not bound this journal.
   Fix: Keep the existing journal format and stop at a fixed budget. Requests and responses now have a 16 MiB cap and the journal a 256 MiB cap. The outer environment still owns its total disk quota.
   If we skip it: Concurrent long attempts can fill the worker's disk even when individual tool results are capped.

6. The allowed turn count exceeded Miles' session node limit. Current fix: Config::validate in src/runner.rs. Native evidence: Miles miles/rollout/session/v2/tree_trajectory.py, MAX_NODES=1024.
   What this is: Each policy or summary request adds a node to the same Miles session.
   Problem: The first implementation accepted max_turns=10000. A run that compacts before each following turn uses two nodes per turn and reaches Miles' hard 1024-node limit well before that configured bound.
   Fix: Limit this profile to 512 policy turns. At most 511 intervening summaries then use 1023 nodes. The implementation and README now agree on that bound.
   If we skip it: A configuration accepted by the runner is guaranteed to fail inside Miles before reaching its promised limit.

Must fix, open at the end of cycle 1:

7. Poor summary output aborts the training batch as an infrastructure failure. Source: src/runner.rs:284-288 and 389-399; python/miles_grok.py:121-122 and 135-138. Native rule: crates/common/xai-grok-compaction/src/code_compaction/config.rs, MIN_SUMMARY_SEED_CHARS=500.
   What this is: The same policy model generates the summary and the coding steps, and both are training targets under the attempt reward.
   Problem: A summary shorter than 500 cleaned characters becomes SampleRetryError::Empty, then status="error". A length-limited or tool-calling summary also becomes an error. The adapter skips verification and the reward hook aborts the batch, although the policy produced the bad output. The executed failed_compaction_preserves_original_transcript_and_runs_once test currently asserts that wrong classification.
   Fix: Treat invalid policy summary output as a gradable task outcome while leaving transport and service errors ungraded. The single-call path does not need the production retry helper or its 500-character minimum; keep native cleaning, accept a nonempty valid short summary, and reject malformed or incomplete summaries without replacing context.
   If we skip it: An ordinary policy mistake stops the rollout batch instead of receiving its task reward. Valid short summaries also fail without an RL-specific reason.

8. Two real native-tool tests are failing. Evidence: /Users/p/.codex/artifacts/grok-rl-build-tools/test-cycle-1.log. Sources: src/tools/tests.rs:82 and 131.
   What this is: The native tool fixtures check a real grep and the subprocess environment.
   Problem: After creating a file containing "after", grep did not return that match. The environment assertion also rejected LOGNAME. I independently reproduced that zsh creates LOGNAME even with env -i; this particular name is not proof of inherited credentials. Grep's native default is Content, so its expected match must not be weakened without finding the cause.
   Fix: Diagnose the actual grep response and fix the startup/tool integration or fixture from that evidence. Permit OS-generated LOGNAME while preserving the test's secret-inheritance check, then rerun the complete Rust crate tests.
   If we skip it: The declared eight-tool path has an unverified search failure, and the security fixture remains red.

9. Disabling login capture still executes the host's shell startup file. Sources: src/tools.rs, new_local_with_login_shell_capture(false); crates/codegen/xai-grok-tools/src/computer/local/terminal.rs:696-697 and 3195-3211. The tools implementer discovered this during the first test failure investigation; this review independently traced and confirmed the code path.
   What this is: The attempt explicitly requests no login-shell capture and supplies a filtered tool environment.
   Problem: The native backend skips its static-shell path when that flag is false, then unconditionally calls its legacy capture_login_env helper. That helper starts a login shell and sources the host HOME startup file before the filtered tool command starts. It inherits the parent environment and its probe is outside the attempt's process scope. A startup file that writes a marker or launches a service therefore runs despite the opt-out.
   Fix: Make the legacy capture honor the existing login_shell_capture flag while preserving the default true behavior. Add a regression that the false path does not initialize or capture login state.
   If we skip it: Attempts execute hidden host startup commands and may create processes or side effects outside their intended lifecycle. The documented no-login-capture behavior is false.

The review also checked exact assistant JSON replay, argument spelling, schema rejection before tool dispatch, duplicate-ID rejection before a batch writes, no production prompt or default-tool injection, per-attempt todo/terminal ownership, explicit child environment, image-output rejection, and the grader error path. The summary generation is intentionally trained once under the attempt reward. Its copied text after compaction is prompt context; inclusion of the generated summary is an explicit design choice, not a finding.

Verification at cycle 1 freeze: the independent Python command passed all 8 tests in 2.410 seconds using the real Miles session URL helper. The build log records a successful cargo check in 49.39 seconds. cargo test built the test target in 42.70 seconds, then ran 10 tests: 8 passed and 2 failed in 1.09 seconds. The failures are finding 8. The passing compaction-failure test exposes finding 7 because its expected outcome is wrong. A scripted endpoint does not prove tokenizer parity or an optimizer update.

Verdict: Fix 7, 8 and 9 first. The six earlier source changes are present; cycle 2 must review the remaining fixes and rerun execution checks.
Not checked: GPU training, a selected model's tokenizer/tool parser, live v2 sample collection, external sandbox isolation, SIGKILL container teardown, or unrelated Grok application and ERP code.
