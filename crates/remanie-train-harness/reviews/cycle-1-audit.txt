What this repo does:
This audit covers the new RL crate and the Grok and Miles code it directly uses. The executable runs a coding attempt, keeps native tool state alive through context compaction, and leaves token recording and training to Miles. I assumed many independent disposable environments with one sequential agent in each.

Cycle 1 audit, 2026-10-27. The audit read the crate's entry point, request loop, templates, tool registry, tests, Python adapter, README files, Cargo registration and lockfile. It traced the native shell environment policy, process scope, terminal lifecycle and log caps, concise file and shell tools, todo state, task output wrappers, and compaction validation. It also read Miles' agent callback wrapper, URL helper, strict message matcher, v2 tree, sample assembly, leaf picker, default postprocessor, and reward callback dispatch. No implementation files were changed by this audit.

The first implementation had six concrete findings fixed during the pass: malformed tool calls reported as completion, a compaction trigger missing new tool output, large process logs copied into compacted context, an unbounded verifier await, an unbounded request journal, and a turn limit above Miles' node cap. Their cases, source evidence and fixes appear as findings 1 through 6 in cycle-1-review.txt. Three additional issues remain at this cycle's freeze.

Must fix:

1. The summary path treats policy output as an infrastructure error. Source: src/runner.rs:284-288 and 389-399, the native compaction MIN_SUMMARY_SEED_CHARS=500 rule, and python/miles_grok.py:121-122 and 135-138.
   What this is: The trained policy generates summaries as part of its attempt.
   Problem: A short, length-limited or tool-calling summary stops the attempt with status="error". The adapter then skips grading and its reward hook aborts the batch. The 500-character production minimum also rejects a usable short summary without an RL-specific reason.
   Fix: Use one summary call with native cleaning and explicit checks. A bad policy summary should produce a gradable invalid_response outcome with no context replacement; transport and server failures should remain errors. A nonempty short summary does not need the production minimum or retry abstraction.
   If we skip it: Normal policy mistakes stop training batches instead of receiving a task reward.

2. The native grep and environment tests do not pass. Evidence: /Users/p/.codex/artifacts/grok-rl-build-tools/test-cycle-1.log. Sources: src/tools/tests.rs:82 and 131.
   What this is: These tests exercise the actual native tools, beyond a mocked API contract.
   Problem: Grep missed the expected "after" result after a real edit, and the environment check rejects LOGNAME. Native grep defaults to content output. A separate env -i experiment confirmed that zsh creates LOGNAME itself, so that one failure is a fixture issue rather than evidence of secret inheritance.
   Fix: Inspect the actual grep response and correct the proven cause; do not replace the match assertion with a weaker one. Admit OS-generated LOGNAME in the environment test and rerun the Rust suite.
   If we skip it: Search behavior remains unverified and the security fixture cannot provide a passing regression check.

3. The native opt-out still runs login-shell capture. Sources: src/tools.rs, new_local_with_login_shell_capture(false); crates/codegen/xai-grok-tools/src/computer/local/terminal.rs:696-697 and 3195-3211.
   What this is: The crate disables login capture when it creates the terminal backend.
   Problem: The native backend still enters the legacy capture helper, which starts a login shell and explicitly sources the host HOME startup file with the unfiltered parent environment. A startup script that writes a marker or launches a service runs before the attempt command and outside its process scope. The tools implementer found this during test investigation; this audit independently confirmed the call path.
   Fix: Gate legacy capture on the existing login_shell_capture flag and test the false path. Keep the production default true behavior unchanged.
   If we skip it: Hidden startup code and its side effects run despite the training profile's opt-out, and the documented lifecycle guarantee is inaccurate.

The following boundaries matter for the supported workload.

Each ToolSession owns its terminal, todo state, process scope and fresh session directory. Native lookup and cancellation can therefore reach only that attempt's terminal tasks. The registry contains exactly eight native tools, checks their names again before each model request, and supplies no subagent backend, MCP tools, memory backend or skill collection. Input schemas reject unknown tools and fields before dispatch. The catalog retains the agreed argument descriptions and first-sentence tool descriptions.

Native defaults are unsuitable for training without explicit setup. ShellEnvironmentPolicy otherwise inherits every parent variable and skips secret-name exclusions. This crate supplies inherit=None, a fixed PATH and fresh HOME/TMPDIR, and requests disabled login-shell capture. The requested opt-out is ineffective until finding 3 is fixed. The environment test inspects only variable names so a failing security assertion does not print secret values. The native output log default is 5 GiB and background lifetime 10 hours; main.rs sets a 16 MiB log cap before starting threads and the runner imposes its own attempt deadline.

The process scope kills registered native process groups on normal completion, errors and Drop. The Python adapter also terminates the Rust process on cancellation. Native shell commands start separate process groups, so killing the Rust process group alone cannot clean up shell descendants after SIGKILL or a crash. README.md:5 and 73 assign that case to destruction of the outer sandbox. This is a documented deployment boundary, not an implemented isolation mechanism. The tests and local process scopes do not prove it.

The adapter strips the caller's environment before launching Rust and keeps the verifier selection out of the child configuration. The verifier must remain outside the environment accessible to model-written code. A fresh directory and an environment allowlist do not restrict absolute file reads, network access, process inspection or arbitrary shell execution. The source does not claim otherwise. Running this raw executable beside trainer credentials or private tests is outside its supported trust assumptions.

The Python adapter returns separate runner_error and grader_error metadata. Miles' agentic wrapper catches agent exceptions and still collects recorded samples, so the required reward hook is essential. This hook refuses missing or error results and raises instead of manufacturing a reward of zero. A verifier's finite zero remains a valid task score. The audit traced both single-sample and list reward calls in Miles and checked the adapter's matching signatures.

The Rust loop replays the returned assistant JSON without normalizing tool arguments or stripping reasoning fields. Miles' strict matcher then has the original template-relevant values needed to continue recorded tokens. Compaction uses the same traced endpoint and generates a new root after the summary. Miles v2 retains roots with different prompts and masks shared generated prefixes in its default postprocessor. The summary generation intentionally receives the attempt reward once; its later copy is prompt context. Source inspection supports this route, but the selected model's actual template and parser still need a live parity check.

Requests, responses and process logs now have explicit size limits, and the request journal stops at 256 MiB. The byte-based compaction trigger is an estimate, not a tokenizer. A caller must choose a threshold below the policy model's real context limit. Overflow fails the attempt; no silent history truncation or retry changes the recorded trajectory. Todo and task metadata survive compaction, while prior raw responses remain in the journal and Miles owns token evidence.

The workspace must be provisioned before the adapter runs. The adapter does not reset a repository, allocate distinct paths for repeated dataset samples, build containers, or remove attempts. Those omissions are explicit in both README files. A real launcher must supply fresh workspace/session paths for every attempt and own cleanup; a static dataset path reused for multiple samples is not sufficient. No Harbor, GKE, training optimizer, or production service was changed by this crate.

The Cargo change adds the crate and its package entry without upgrading upstream dependencies. Reusing the native tools keeps the large upstream dependency graph. Extracting that graph or replacing the tools would be a separate project and was not needed for this implementation. The original license and third-party notices remain available.

Verification at cycle 1 freeze: all 8 adapter fixtures passed independently in 2.410 seconds against the real Miles URL helper. The recorded cargo check passed in 49.39 seconds. The Rust test target built in 42.70 seconds and ran 10 tests, with 8 passing and 2 failing in 1.09 seconds. The two failures are audit finding 2. The passing failed-compaction fixture still expects an infrastructure error and must change with audit finding 1. The executed passing checks covered native todo isolation, exact assistant replay, real file editing through the runner, malformed call rejection, no partial writes for duplicate IDs, compaction state retention, and native process cleanup on an attempt deadline.

Verdict: Fix audit findings 1, 2 and 3 before approving the code. Cycle 2 must review those changes independently and rerun checks. Real training also requires the documented external isolation and tokenizer validation.
Not checked: unrelated Grok UI and integrations, ERP code, all transitive dependency internals, live provider calls, model-specific TITO parity, GPU training, production sandbox enforcement, or cleanup after forced container termination.
